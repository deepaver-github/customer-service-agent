# Special Care Australia — AI Care Assistant

## What This Is

A customer-facing AI assistant for **Special Care Australia**, an NDIS-registered disability support provider. Participants, families, support coordinators, and staff chat with the assistant to look up participant records, find services, ask NDIS questions, and reach a human when needed.

Backend is a FastAPI app using Claude for natural language; frontend is an Angular SPA served from the same origin. This database is the **system of record** for SCA operations (participants, plans, shifts, notes, incidents) — billing is intentionally out of scope and handled by external software (Brevity/Lumary/etc.).

## Tech Stack

- **Backend:** Python 3.10+, FastAPI (async), SQLAlchemy 2.0 (async) + asyncpg, Pydantic BaseSettings
- **LLM:** Claude via Anthropic Python SDK (`anthropic`, model `claude-sonnet-4-6`)
- **Database:** PostgreSQL 16 via Docker Compose (SQLite/aiosqlite in tests)
- **Frontend:** Angular 20 (standalone components, signals) + Tailwind CSS v3, marked + DOMPurify for markdown, `@microsoft/fetch-event-source` for SSE
- **Config:** `.env` (secrets) + `agent_config.yaml` (agent behavior)
- **Testing:** pytest + pytest-asyncio (98 passing, 4 known-failing streaming-mock tests unchanged from main, 3 Postgres-only immutability tests skipped by default)
- **Logging:** structlog (structured JSON)
- **Build:** hatchling via `pyproject.toml`; Angular via `@angular/build:application`

## API Endpoints

All endpoints below (except `POST /auth/login` and `GET /health`) require a `Authorization: Bearer <token>` header. Tokens are issued by `POST /auth/login` and last 7 days.

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | /auth/login | none | `{email, password}` → `{token, expires_at, user}` |
| POST | /auth/logout | bearer | Revoke the current token |
| GET | /auth/me | bearer | Current user (id, email, role, staff_id, participant_id, name) |
| POST | /chat | bearer | Send message, get response |
| POST | /chat/stream | bearer | Send message, get SSE stream |
| POST | /sessions | bearer | Create session; stamps `user_id = current_user.id`. Staff role auto-fills `staff_id`, participant role pins `participant_id` to self |
| GET | /sessions | bearer | Cursor-paginated session list, scoped to caller. Admin also sees every `escalated` session across users (see Chat scoping below) |
| GET | /sessions/{id} | bearer | Get session + message history. 403 unless caller owns it or (admin AND status=escalated) |
| DELETE | /sessions/{id} | bearer | Close a session. 403 unless caller owns it (admin override does NOT extend to writes) |
| GET | /participants | staff only | List with search + status filter |
| POST | /participants | staff only | Create participant; 409 on duplicate live `ndis_number` |
| GET | /participants/{id} | staff or self | Full detail with contacts/plan/goals/shifts/clinical/audit-log (participant role 403s on other records) |
| PATCH | /participants/{id} | staff only | Partial update (Pydantic `exclude_unset`); empty body → 400, bad enum → 400 with allowed values, missing id → 404, duplicate live `ndis_number` → 409 |
| GET | /staff | staff only | List staff |
| GET | /knowledge | staff only | List knowledge articles |
| GET | /dashboard/stats | staff only | Aggregate counts |
| GET | /health | none | Health check |
| GET | / (and any browser navigation) | none | Angular SPA shell (`app/static/index.html`) — see SPA-fallback note below |

**SPA fallback.** `app/main.py` uses `SPAStaticFiles` (404 inside the static mount → `index.html`) plus a `spa_fallback_handler` that catches Starlette `HTTPException` 401/404/405 and serves `index.html` *only* when the request is a browser navigation (`GET` with `text/html` in `Accept`). XHR/JSON clients still get the proper status + JSON body — so `/participants/abc` from the browser renders the Angular detail page, while the same URL from `fetch()` without a token gets a real 401.

**Chat scoping.** Every `sessions` row carries `user_id` (FK → `users.id`, `SET NULL` on delete) stamped on create. `GET /sessions` always filters to `user_id == current_user.id`; for `UserRole.ADMIN` it additionally includes any session with `status = escalated` (cross-user oversight). `GET /sessions/{id}` and `DELETE /sessions/{id}` apply the same rule via `_can_view_session` and `_user_can_send_to`. The admin escalated-override is **read-only** — `POST /chat` / `POST /chat/stream` always 403 a write into a session you don't own (admins observe escalations, they don't impersonate the chatter). `repo.list_sessions` is scope-mandatory; with no `user_id` and `include_escalated=False` it returns an empty list, so a future caller can't accidentally leak rows.

## Schema

System of record for SCA. **All four phases of `lucky-sprouting-globe.md` are live** as of 2026-06-03.

**People (Phase 1):**

- `sessions`, `messages` — chat history. `sessions` has nullable `participant_id` (FK to participants), `staff_id` (FK to staff), and `user_id` (FK to users, indexed, `SET NULL` on delete — the authoritative owner column used for scoping; participant_id/staff_id remain for chat-on-behalf-of semantics).
- `participants` — NDIS number, name, DOB, primary disability category, address, comms needs, status. Soft-deleted via `deleted_at`. Partial unique index on `ndis_number WHERE deleted_at IS NULL` (Postgres only).
- `contacts` — per-participant: family, guardian, support_coordinator, plan_manager, GP, advocate, emergency. `is_primary` / `is_emergency` flags.
- `staff` — name, role, NDIS Worker Check / WWCC / police check expiries.
- `participant_staff_assignments` — primary/secondary/do_not_roster with valid_from/to.
- `service_types` — catalog (SIL, personal_care, community_participation, respite, complex_support). No rates — billing is out of scope.
- `knowledge_articles` — markdown body, category, tags. Powers `search_knowledge`.

**Plans & funding (Phase 2):**

- `plans` — plan number (partial-unique among live rows), start/end dates, management_type (self / plan_managed / agency_managed), plan manager contact, status.
- `goals` — belong to the participant (survive plan renewal); `current_plan_id` points at the plan currently funding the goal.
- `plan_goals` — many-to-many join with funding_category + priority.
- `service_agreements` — per-participant scope-of-service record (no billing).

**Service delivery (Phase 3):**

- `shifts` — scheduled/actual start+end, status (scheduled, in_progress, completed, cancelled_by_participant, cancelled_by_provider, no_show), cancellation reason, optional `handover_note_id` linking back to a progress note. Indexed by `(participant_id, scheduled_start)` and `(staff_id, scheduled_start)`.

**Clinical & safeguarding (Phase 4):**

- `progress_notes` — `note_type`, content, optional `shift_id` / `incident_id`. `corrects_note_id` is a self-FK used for corrections (never edit a locked note — append a new one). **Immutable once `locked_at` is set** (Postgres trigger blocks UPDATE/DELETE).
- `incidents` — type (reportable / general), category, status, plus nullable notification timestamps for NDIS Commission / WorkSafe / Police. No `deleted_at` — close with status.
- `incident_followups` — action / outcome / due / completed.
- `medication_records` — current prescription list (name, dose, route, frequency, PRN flag).
- `medication_administration_log` — append-only ledger of what was administered. **Unconditionally immutable** (trigger blocks all UPDATE/DELETE).
- `restrictive_practices` — type, authorisation reference + dates, FK to behaviour-support-plan document.
- `risk_assessments` — type, level (low/medium/high/critical), controls, `superseded_by_id` self-FK for versioning.
- `participant_preferences` — one row per preference (communication / food / routine / sensory / trigger / like / dislike) with priority.
- `documents` — polymorphic pointer (`subject_type` + `subject_id`); `storage_url` points at S3/blob (backend wiring is still out of scope).

**Auth (post-Phase 4):**

- `users` — auth identity. Unique-among-live `email` (partial unique index), scrypt `password_hash`, `role` enum (admin / manager / coordinator / support_worker / participant), optional `staff_id` or `participant_id` FK linking the auth identity to its operational record, `is_active`, `last_login_at`. Soft-deleted via `deleted_at` and audited.
- `auth_sessions` — opaque Bearer tokens. `token` is the primary key (64-char `secrets.token_urlsafe(48)`), with `user_id`, `expires_at` (default 7 days), and nullable `revoked_at`. Deliberately *not* in `AUDITED_TABLES` — high-churn, security-sensitive.
- Password hashing is stdlib `hashlib.scrypt` (OWASP-accepted parameters, no extra dependency).
- Role helpers in `app/memory/models.py`: `STAFF_ROLES = {admin, manager, coordinator, support_worker}` — anything outside this set (currently just `participant`) gets 403 from `current_staff`.

**Audit + immutability triggers:** defined in `app/memory/database.py`.
- Audit: every table in `AUDITED_TABLES` (18 tables across all phases + `users`) gets `<table>_audit_trigger` via `audit_trigger_func()`. Soft-delete is itself audited because it's an UPDATE.
- Immutability: `progress_notes_immutability_trigger` blocks UPDATE/DELETE when `locked_at IS NOT NULL`; `med_admin_immutability_trigger` blocks UPDATE/DELETE unconditionally. Both functions raise PL/pgSQL exceptions with the offending `id`.
- Skipped (intentional): `service_types`, `knowledge_articles`, `participant_preferences`, `sessions`, `messages`, `auth_sessions`.

## Key Design Decisions

- **No LangChain** — Claude's native tool-use API. Simpler, easier to debug.
- **Decorator-based tool registration** — `@register_tool` auto-converts type hints to JSON Schema.
- **Escalation as a tool** — Claude calls `escalate` like any other tool. Cleaner than parsing JSON from text.
- **Audit via Postgres triggers, not Python** — every audited table gets a row in `audit_log` automatically on INSERT/UPDATE/DELETE. Soft-delete (`deleted_at` update) is itself audited because it's an UPDATE.
- **System of record, billing excluded** — SCA's operational truth lives here; billing flows go through external tools that consume exported shift records.
- **Alembic baseline in place** — `alembic.ini` + `alembic/env.py` (async, reads `DATABASE_URL` from `app.config`) + a no-op baseline revision `0001_baseline` that marks the current schema as head. `init_db()` still calls `Base.metadata.create_all` on startup, which is fine while there's no production data. Once real participant data lands, stamp the DB once with `alembic stamp head` and switch new schema changes to `alembic revision --autogenerate -m "..."` + `alembic upgrade head` (and drop the create_all call).
- **Auth via opaque DB-backed Bearer tokens** — not JWT. Trade-off: a token lookup costs a row read on every authenticated request, but logout is instant (single UPDATE), there's no key-rotation operational burden, and we can list every active session per user trivially. `scrypt` (stdlib) for password hashes — no `passlib`/`bcrypt`/`argon2-cffi` dependency.
- **Role-scope at the route layer, not via middleware** — each route declares `Depends(current_user)` or `Depends(current_staff)`; participant-vs-self scoping uses `participant_can_access()` inside the route. Easier to reason about than blanket middleware, easier to override in tests (chat-API tests override `current_user` to a fake staff user, avoiding token threading).
- **Single-origin SPA + API + SPA fallback** — Angular builds into `app/static/`, FastAPI serves it via `SPAStaticFiles` mounted at `/`. A custom Starlette exception handler catches 401/404/405 on browser navigations and returns `index.html` so Angular's router can render `/login`, `/participants/:id`, etc. on direct visits. XHR clients still get proper JSON error bodies. CORS allows `http://localhost:4200` for dev (Angular dev server).
- **Single deployment** — not multi-tenant. Branding (logo, colors, agent personality) is hardcoded for SCA.
- **Railway start command runs in exec form** — for Dockerfile deploys, a custom `startCommand` is NOT shell-interpreted, so `&&` and `${PORT}` are passed literally. Seed via `railway.toml` `preDeployCommand`; wrap the run command as `/bin/sh -c 'uvicorn … --port ${PORT:-8001}'`. (The `Dockerfile` `CMD` is shell-form, so it expands `${PORT}` fine on its own.)

## Running

```bash
# 1. Start PostgreSQL (foreground or detached)
docker compose up -d

# 2. Activate venv
.venv\Scripts\activate

# 3. First-time setup or after a schema change: reset volume + seed
docker compose down -v && docker compose up -d
python -m app.memory.seed     # creates tables + triggers, inserts NDIS samples

# 4. Run the backend
uvicorn app.main:app --reload --port 8001

# 5. Frontend dev (separate terminal — proxies API calls to :8001)
cd frontend && npm start      # http://localhost:4200

# OR — production frontend build served by FastAPI directly:
cd frontend && npm run build  # builds into ../app/static/
# then visit http://localhost:8001

# Tests
pytest -v                     # 98 pass, 4 known-failing streaming-mock tests, 3 skipped (Postgres-only)
# To run the Postgres-only immutability tests:
$env:TEST_DATABASE_URL = "postgresql+asyncpg://agent:agent@localhost:5432/customer_service"
pytest tests/test_immutability.py -v
```

Port 8000 is blocked on this machine — use **8001**.
